# Event 逻辑关系规范表

版本：`event-relations/0.2`。

状态：已接入 event-workflow/0.2 的推断提示词、输出 Schema、独立关系审查与绘图。
运行定义位于 `agentvast/semantic/event_relations.py`，测试校验其与本表一致。已有推断结果保持原版本含义，
不能仅因类型名称相同就视为符合本规范。

## 目标和方向

本表描述对数据分析任务的信息流、决策、纠错、验证、综合和交付有解释价值的 Event 联系。
逻辑关系类型只能从本表选择；模型不得生成新类型，也不要求每类出现或每个 Event 都有逻辑边。
调用、返回、委派、记录顺序仍由规则关系表达，不以覆盖执行细节为由补造逻辑关系。

每条关系是有证据支持的解释，不是因果已被实验确认。箭头从较早的依据、条件、问题或结果 A，
指向后续使用、行动、复核或更新 B。序列可辅助检查先后，不单独证明联系；跨 Agent 的并行记录
需要结合调用 ID、任务 ID 和产物版本判断，不能仅凭全局 sequence 推定因果。

`CHALLENGED_BY` 和 `SUPERSEDED_BY` 有意采用被动命名，保持“旧结果 → 后续质疑/替代”的 DAG 方向。
它们不绘制“后续证据 → 过去结果”的回边，也不把导致更新的证据关系与版本替代关系混为一条。

## 固定关系表

| 类型 | 中文含义与 A → B | 必须满足的条件 | 不成立的情况 | 最小证据示例（人工示例） |
| --- | --- | --- | --- | --- |
| `PROVIDES_INPUT` | 提供输入：数据/信息/中间结果 → 实际使用者 | A 产出可识别对象或信息；B 的记录明确使用该对象、版本或内容 | 只访问相同路径、讨论同一主题、只有计划而无消费证据 | A 输出清洗表；B 命令参数读取该版本的清洗表 |
| `GUIDES_METHOD` | 指导方法：要求/约束/方案 → 采用该方法的行为 | A 给出范围、指标、方法、交付格式等约束；B 明确采纳并落实 | 泛泛背景介绍、未采纳的建议、计划之间没有后续落实 | A 要求使用中位数；B 计算中位数并报告 |
| `ENABLES_EXECUTION` | 提供执行条件：准备/恢复条件 → 依赖该条件的执行 | A 建立必要环境或能力；B 的记录表明确实依赖它 | 常规初始化、仅因安装在执行之前、无法说明必要依赖 | A 解决缺失依赖；B 随后成功执行此前被该依赖阻断的脚本 |
| `TRIGGERS` | 触发行动：要求/决定 → 具体后续行动 | A 明确提出行动；B 对应该行动且关联可核查；更具体类型不适用 | 单纯 tool_use 配对、普通函数调用、时间相邻、笼统“接下来分析” | A 要求补充地区对比；B 新增对应分析 |
| `MOTIVATES_INVESTIGATION` | 引出调查：异常/差异/线索 → 定向调查 | A 发现具体疑点；B 围绕该疑点追加检查或探索 | 常规探索、A 没有疑点、B 尚未调查就只是复述结果 | A 发现某日骤降；B 检查当日缺失记录与采集状态 |
| `LEADS_TO_CORRECTION` | 促成修正：问题/错误 → 修正行为 | A 暴露可识别问题；B 针对同一问题实际修改代码、数据处理或方法 | 无关修改、仅有失败、相同条件原样重跑、只声称“已修复” | A 日期解析报错；B 修改异常日期处理代码 |
| `LEADS_TO_RETRY` | 促成重试：失败/阻断 → 同一目标的重新尝试 | A 的失败或阻断明确促成 B 重试；可核查共同目标和重试依据 | 定时运行、普通迭代、两次相似命令但目标不同 | A 请求超时；B 保持同一查询目标再次请求 |
| `LEADS_TO_VALIDATION` | 引出验证：待检验结果/假设/修改 → 实际检验行为 | B 检查 A 对应的准确性、有效性或修改效果，有检验对象和检查记录 | 普通审批、读取但不检查、只计划验证、将任意后续执行称为验证 | A 改正计算代码；B 用样本重新计算并核对预期值 |
| `AUTHORIZES` | 授权执行：明确批准/确认 → 受该批准约束的行动 | A 是可核查的许可或选择；B 明确落实该许可；A 确实决定行动是否或如何进行 | 普通“好的”、系统成功状态、计划提交本身、事后确认 | A 批准选定方案；B 按该方案开始此前等待批准的执行 |
| `CONTRIBUTES_TO_MERGE` | 汇入综合：分支产出 → 综合分析/汇总 | A 是独立分析或子任务产出；B 明确把它纳入多个分支的汇合 | 工具返回就叫汇合、单一输入直接转发、分支结果未被采用 | A 子 Agent 给出地区分析；B 联合地区与时间分析形成综合报告 |
| `SUPPORTS_RESULT` | 支撑结论：分析/验证证据 → 采用该证据的结论/交付 | B 的可识别结论由 A 的结果或检验支撑，关键对象、数值和口径一致 | 单纯生成文件、摘要相似、计划支撑结果、结论没有实际采用证据 | A 输出缺失率 30%；B 报告引用该缺失率并给出限制 |
| `CHALLENGED_BY` | 被质疑/反驳：原结果/假设 → 后续反证或质疑 | B 明确指出 A 的问题、相反证据或失效条件；指向同一对象和口径 | 不同样本/时间/指标的数值差异、普通补充、自动认定所有差异为错误 | A 报告全量均值；B 发现该计算漏掉一组数据，质疑此均值 |
| `SUPERSEDED_BY` | 被替代：旧方案/结果/要求 → 明确替代版本 | B 明确更新或替代 A；可辨别共同对象和版本/范围变化；旧项不再作为当前依据 | 同路径再次写入、增加附录、并存方案、只有差异没有替代声明 | A 使用旧筛选口径；B 明确撤销旧口径并确定新的任务口径 |

原有六类：`PROVIDES_INPUT`、`TRIGGERS`、`LEADS_TO_CORRECTION`、`LEADS_TO_VALIDATION`、
`CONTRIBUTES_TO_MERGE`、`SUPPORTS_RESULT`。其余七类为本规范新增。

## 选择规则：避免重叠与泛化

同一对端点默认选择一条最能解释任务联系的主关系，不为增加连线而同时输出泛化关系。
确有两种独立语义时可在派生数据保留第二条，但必须各有证据；绘图需要明确主标签与次关系，
不能像当前按端点去重的实现那样静默丢失第二种含义。

- 方法或范围被落实，选 `GUIDES_METHOD`；许可决定行动，选 `AUTHORIZES`；一般要求引出行动
  且前两者不适用，才选 `TRIGGERS`。
- 数据被消费，选 `PROVIDES_INPUT`；分支被综合，选 `CONTRIBUTES_TO_MERGE`；证据被结论采用，
  选 `SUPPORTS_RESULT`。源 Event 可以分别对不同目标成立不同类型。
- 线索引出追查，选 `MOTIVATES_INVESTIGATION`；已有对象被检验，选 `LEADS_TO_VALIDATION`。
  B 调查后同时完成复核时，按该段记录的主要行为选择，有独立证据才保留次关系。
- 问题 → 修改选 `LEADS_TO_CORRECTION`；失败 → 再次尝试选 `LEADS_TO_RETRY`；修改 → 复核选
  `LEADS_TO_VALIDATION`。通常是不同端点的链，而非同一条边上的三个标签。
- 原结果 → 后续反证选 `CHALLENGED_BY`；旧版本 → 新替代版本选 `SUPERSEDED_BY`。有反证不代表
  已经产生替代版本；同一批数据的新数值也不自动证明旧数值错误。
- `ENABLES_EXECUTION` 必须能指出阻断或必要条件；普通准备仅作为背景行为或规则联系。

## 候选范围与成立门槛

先生成候选 Event 对，再让模型按本表判定；候选只是待审查联系，不是关系事实。
候选优先来自显式引用、任务/调用链、具体数据消费、可识别产物版本、问题与后续修复、
检验对象、分支汇合，以及用户范围修订。

同任务、同轮次、同路径和规则邻接可以用于发现候选，但不能单独作为成立依据。
允许跨轮次、跨 Agent、跨阶段建立关系；需要明确的任务延续、引用、消费或版本依据，
不强制限制在固定的相邻 N 个 Event，也不强制必须已有直接规则边。
候选选择策略和覆盖范围应记录，以免未进入候选的联系被误当成不存在。

每条候选关系必须回答：

1. A 提供了什么信息、条件、问题、要求或旧版本？
2. B 的哪一段记录表明实际消费、落实、回应、检验或更新了它？
3. 这条关系符合表中哪项条件？是否触发排除条件？

两端短引文只是必要条件。出现相同词语、数字或文件名，不能替代联系本身的证据。
计划可作为“要求/方案”的来源，但执行、消费、纠错、验证等目标必须有相应记录；
只有计划时不标记为实际完成。摘要不够核查时回查原 Event，仍不足则保留候选或放弃建立。

## 置信度与展示状态

置信度不表示经过校准的准确率，不能仅凭模型自评决定是否绘制。

| 状态 | 门槛 | 默认绘图建议 |
| --- | --- | --- |
| `accepted` | 类型条件成立，联系可核查，无已知矛盾，证据与结构审查通过 | 绘制；核心主干可优先考虑 |
| `candidate` | 存在合理线索，但消费、版本、对应任务或关系依据尚不充分 | 不进入默认主图，可按需查看 |
| `rejected` | 不符合类型条件，存在排除条件/矛盾，或引用无效 | 不绘制，保留拒绝原因供诊断 |

`high/medium/low` 作为 accepted/candidate 的辅助属性；低置信度默认留在候选层。
这些状态已接入 0.2：`relation_assessments` 保存全部审查结果，`logical_relations` 仅保存 accepted。
旧版 0.1 继续只读展示，界面明确提示其未按新表审查；点击「按新规范推断」升级。
语义审查可以由第二次模型审查或人工完成；结构、端点、引文、环和确定性矛盾检查由代码完成。
不能把模型复核或引文校验称为“已证实因果”。

## 后续推断输出与绘图接口

沿用 `from/to/type/label/explanation/evidence_refs/confidence`；已补充以下审查字段：

- `catalog_version`：本规范版本，至少在整个推断结果上记录一次。
- `connection_basis`：可核查的连接依据，例如 B 使用了 A 的哪项输出或回应了哪项问题。
- `review_status`：accepted/candidate/rejected；模型可提出建议，最终状态由审查步骤确定。
- `limitations`：资源版本、输入截断、仅报告未核实等限制。
- `context_evidence_refs`：可选链路补充引用，例如证明失败与重试之间发生修正的中间 Event；
  与仅引用两端的 `evidence_refs` 分开存放。所有补充引用同样校验 ID、字段和原始引文，不能代替两端证据。

规则关系继续独立保留，逻辑关系不改写原 Event。当前主图仅采用 accepted 的任务逻辑边，
显式调用约束辅助构图，规则补充仍按原有策略显示；规则执行细节按需展开是后续功能。
时间顺序不升级为业务逻辑。
`SUPERSEDED_BY` 不删除旧节点或旧证据，只标明其已被后续版本替代。
节点重要性另行评估，不能由关系类型或边的数量直接决定。

接入已同步更新后端 Schema/提示词、审查器、前端类型与图例，关系规范版本和完整定义哈希进入缓存键。
原始输入提示哈希、模型、思考强度一致且证据校验通过的旧摘要可跨版本复用；旧逻辑关系重新推断，
不能自动升级。成功生成前保持旧结果可读，替换时归档到 `derived/event_workflows/`。

处理链路：全量 Event 摘要 → 按固定表提出候选关系 → 原引文/结构校验 → 独立模型审查
（消费全量摘要、规则关系、候选关系与两端原始字段有界摘要）→ 代码执行置信度/方向/环门槛
→ accepted 关系参与重要性评估和绘图。
候选发现目前由全局提议请求按候选范围规则完成，尚未引入单独的确定性候选检索器。
审查请求与修复请求同样受完整输入预算限制，超出时保留检查点并停止。

## 最小验收案例

1. 日期解析失败 → 修改解析代码 → 重跑复核，分别得到 correction 和 validation；直接原样重试
   时使用 retry，不能把无修改的重试称为纠错。
2. 计划提交 → 用户批准 → 执行：批准到执行可为 authorizes；计划到批准不冒充结果验证。
3. 两个分支报告 → 综合结论：仅被实际采用的分支建立 merge；收到但未采用的分支无逻辑边。
4. 旧口径 → 用户明确改为新口径 → 新口径执行：旧新要求用 superseded_by，新要求到执行用
   guides_method；保留旧执行历史。
5. 两次访问相同路径但版本或用途未知：可生成候选，不接受 provides_input。
6. 先报告结论、后出现反证：旧结论到后续反证用 challenged_by，随后有明确替代结论才增加
   superseded_by；不为画图构造指向过去的回边。
7. A 与 B 时间相邻且摘要相似，无可核查连接依据：不生成逻辑关系。
