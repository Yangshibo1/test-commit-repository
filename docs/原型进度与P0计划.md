# AgentVAST 原型进度与 P0 计划

## 1. 当前结论

截至 2026-08-22，AgentVAST 已经形成可运行的端到端记录闭环：核心 SQLite 状态机、CLI、
Claude Plugin/Hook、规范化 JSON、Web 终端与 Plan 控制、DAG 前端解析和 Reviewer 后端均已
进入代码。当前尚未达到稳定发布状态，剩余工作以真实 Claude Code 手动验收、自动测试同步和
前端最新源码构建验证为主。

当前定位：

```text
设计与核心记录闭环已经完成
SQLite、CLI、Plugin/Hook 和 schema 1.3 导出已经实现
Web P0/P1 交互代码与 DAG 前端解析已经接入
Reviewer 后端已经实现，前端展示与完整自动化验收仍待完成
```

第 2—7 节保留早期 P0 评估作为开发历史；其中“尚未实现”描述已被第 8 节以后的实施记录
取代，不代表 2026-08-22 的当前功能状态。

本阶段继续坚持个人系统边界。开发只优先服务两个目标：

1. 完整记录以语义 Node 为颗粒度的 Agent 数据分析 workflow。
2. 约束 Agent 按照可记录、可解释且颗粒度合理的方式进行分析。

## 2. 已完成内容

- AgentVAST 只记录和校验，不执行数据分析。

## 3. 真实端到端验证结果

最近的真实 Run 已经证明以下能力有效：

- Run创建；
- Claude session绑定；
- 初始输入文件记录；
- SHA-256计算；
- SessionStart Hook；
- 部分工具门禁；
- 失败事件诊断；
- JSON导出。

但没有形成成功 workflow：

```json
{
  "plan": null,
  "steps": [],
  "status": "active"
}
```

失败原因：

1. Claude自动生成`cd "project" && python -m agentvast.agent_cli ...`。
2. 当前门禁拒绝所有包含`&&`和换行的命令。
3. 合法`set-plan`和`start-step`被误拦截。
4. `PowerShell`未被Hook覆盖。
5. Claude通过`PowerShell`读取数据并完成分析。
6. 实际分析没有进入语义Plan和Step。

所以当前只能认定为“可单元测试的技术原型”，不能认定为“可稳定使用的MVP”。

## 4. 主要遗留问题

### 4.1 运行时门禁

- 合法记录命令带`cd ... &&`时被误拦截。
- 多行JSON payload被误拦截。
- `PowerShell`未进入门禁。
- 当前工具短名单可能遗漏Web、子Agent和未来新增工具。
- 未知实质性工具可能形成旁路。
- 记录命令失败后Claude可能尝试寻找替代工具继续分析。

### 4.2 Stop和Run完成

- Stop只检查active Step和待处理人工输入。
- 没有强制要求存在Plan。
- 没有强制要求至少完成一个Step。
- 没有强制要求执行`finish-run`。
- 没有检查关键门禁旁路或记录器错误。
- Claude可能输出最终答案而Run仍为`active`。

### 4.3 最终字段尚未落地

当前代码仍使用旧字段：

```text
step_type
expected_output_roles
operation_types
parameters
algorithms
processing_result对象
analysis_conclusion对象
output role
structured_summary
```

需要迁移到：

```text
operation.summary
operation.commands
operation.programs
result_summary
analysis_conclusion字符串或null
```

文件大小、完成条件和原始事件可以继续保留在内部SQLite，但不进入对外JSON。

### 4.4 Plan与Step约束

当前只验证`node_id`存在于最新Plan，没有：

- 在Step上保存`plan_version`；
- 校验Plan依赖是否已由completed Step满足；
- 强制依赖变化前修订Plan；
- 防止Plan Revision隐藏已完成历史；
- 根据Plan Revision自动推导实际Step依赖。

### 4.5 规范化导出（历史状态，后续已实现）

当前导出混合了运行状态和诊断日志，尚未实现：

```text
schema_version
run
plan_revisions
steps
human_interventions
file_lineage
```

同时存在：

- 只导出最新Plan；
- `payload`和`payload_json`重复；
- 原始Hook事件混入语义记录；
- 没有自动刷新规范化JSON；
- 没有显式文件血缘派生。

### 4.6 自动观察（历史状态，后续已实现）

尚未实现：

- 从Bash和PowerShell提取真实分析命令；
- 过滤AgentVAST自身记录命令；
- 自动识别实际Python程序；
- 将程序和命令规范化到active Step；
- 自动发现程序内部产生的输出文件。

### 4.7 人工介入（历史状态，后续已实现）

已经有捕获、分类和apply骨架，但尚未完整实现：

- 自动关联介入发生时的active Step；
- 自动关联当时Plan Revision；
- 普通交流不进入最终JSON；
- challenge触发验证或纠正Step；
- 真实Claude端到端闭环。

### 4.8 DAG与前端（历史状态，后续已实现）

尚未实现：

- 从规范化JSON生成DAG；
- Step、文件和人工介入节点；
- input、output、depends_on和influenced边；
- `dag.json`；
- 新Run JSON前端解析；
- 以`path + sha256`区分文件版本；
- 根据Step sequence和DAG边布局。

当前前端仍读取旧版多文件PROV格式，并依赖`node_01`等文件名布局。

### 4.9 新旧系统并存

仓库同时存在旧`tracker/prov_dag/step_details/mcp_server`与新
`workflow_store/agent_cli/plugin_hook`。

后续规则：

- 新`workflow_store`是唯一事实来源；
- 旧PROV代码只作为兼容适配器；
- 不继续扩展旧记录接口；
- DAG和旧文件格式从新规范化JSON派生。

## 5. P0范围

P0只完成真实记录闭环，不包含DAG和前端迁移。

### P0-1 记录命令安全识别

- 允许单个直接记录命令。
- 允许`cd 当前项目 && 单个记录命令`。
- 允许单引号JSON payload内部换行。
- 拒绝其他项目目录。
- 拒绝追加分析命令、管道、重定向和命令替换。
- 对payload进行JSON和action校验。

### P0-2 工具门禁覆盖

- 加入PowerShell。
- 覆盖Web、子Agent和其他实质性工具。
- 未知工具默认按安全分类处理。
- Hook失败时fail-closed。
- 增加旁路审计事件。

### P0-3 最终字段迁移

- SQLite支持`plan_version`。
- Step迁移到`result_summary`和字符串`analysis_conclusion`。
- Agent不再提交算法、参数、操作类型和输出角色。
- 命令和程序来自Hook自动观察。
- 对外导出隐藏内部控制字段。
- 保留兼容迁移，避免已有数据库无法打开。

### P0-4 Plan–Step强绑定

- 每个Step对应当前Plan Revision中的Node。
- Step保存`plan_version`。
- Node依赖必须由completed Step满足。
- 依赖或目标变化必须先创建Plan Revision。
- 已完成Step不允许被后续Plan隐藏。

### P0-5 Stop和finish-run

- 无Plan时禁止结束。
- 没有completed Step时禁止结束。
- active Step未完成时禁止结束。
- 人工输入未解决时禁止结束。
- 没有成功`finish-run`时禁止正常结束。
- 存在关键一致性错误时`finish-run`失败。

### P0-6 端到端验证

至少验证：

```text
创建Run
→ Claude提交Plan
→ 启动Step 1
→ 读取声明输入
→ 完成Step 1
→ 启动并完成Step 2
→ finish-run
→ 导出规范化JSON
```

同时验证：

- PowerShell无法绕过。
- 无active Step的Read/Bash被拒绝。
- 非法记录命令无法绕过。
- Stop不能提前结束。
- 导出不包含原始诊断日志和已删除字段。

## 6. P0验收标准

P0完成必须同时满足：

1. 当前兼容网关下至少完成一次真实Claude Code Run。
2. Run最终状态为`completed`。
3. 至少记录两个completed语义Step。
4. 每个Step能够定位到Plan Revision和Node。

7. 输出符合[记录字段设计.md](记录字段设计.md)。
8. 无active Step时无法读取或执行分析。
9. PowerShell和子Agent不能形成旁路。
10. 全部记录器测试通过。

## 10. Node术语统一

后续对外模型不再同时使用Plan Node和实际Step两个业务概念，统一为Node：

```text
plan_revisions[].nodes = 计划中的Node
nodes[] = 实际执行的Node
```

二者使用相同的`node_id`，实际Node通过`plan_version`指向启动时的Plan Revision。

同步调整：

- 对外顶层`steps`改为`nodes`；
- 实际记录不再输出`step_id`；
- `file_lineage.step_id`改为`file_lineage.node_id`；
- `human_interventions.active_step_id`改为`active_node_id`；
- Agent主命令改为`start-node`和`complete-node`；
- schema版本升级为`1.1`。

SQLite已有`steps/step_id`列和旧命令别名暂时保留用于内部关联与历史兼容，不作为对外概念。

## 11. 真实分析产物门禁

VAST 手动 Run `run_c5ac2d993a2b` 暴露出新的完成真实性问题：虽然十个 Node 都被记录为
completed，但所有输出为空，最后的可视分析系统 Node 没有命令、程序或文件，实际项目中也
没有生成相应成果。因此“Agent 提交了结果摘要”不能作为 Node 完成的充分条件。

本轮原型采用四类正式产物：

```text
result/<run_id>/code/
result/<run_id>/data/
result/<run_id>/report/
result/<run_id>/visualization/
```

约束如下：

1. AgentVAST 为新 Plan Node 分配稳定编号 `node-001`、`node-002`，Agent 提交的名称只作别名。
2. 每个产物文件名必须带生成 Node 的前缀，例如 `node-002_event_chain.json`。
3. Plan Node 使用 `required_artifacts` 声明由Claude判断的最低产物类别；不强制每个Node
   生成报告，也不强制整个Plan覆盖四类成果。
4. `start-node` 保存四个目录的文件快照。
5. `complete-node` 自动发现本 Node 新增或修改的文件，不依赖 Agent 手工填写输出清单。
6. 缺少要求类别、文件为空、文件名不合规，或要求代码但程序未真实执行时，Node 不能完成。
7. `finish-run` 检查已记录文件没有被后续删除或修改，不要求四类产物全部齐全。
8. 实质 Python 分析必须保存为 `.py` 或 `.ipynb` 并执行；内联 `python -c` 被门禁拒绝。
9. 对外 schema 从 `1.1` 升级为 `1.2`，增加 `run.result_root` 和
   `plan_revisions[].nodes[].required_artifacts`。

该版本记录随后继续演进；当前代码导出 schema `1.3`，新增 Node/Run 的
`analysis_outcome` 与 `recording_warnings` 等可复核状态字段。

这套门禁只验证 Agent 确实留下了可复核的分析过程产物，不判断分析结论是否科学正确，也不
替代人工对报告和可视化的质量评估。

## 12. 2026-07-31 P0 记录真实性优化

本轮代码已完成以下调整，等待用户执行真实 Claude Code Run 手动验收：

### 12.1 完成后记录真实输入

- `start-node` 只接收 `node_id`；
- Node 启动时冻结当时已知的 Run 初始输入和 completed Node 输出版本；执行中首次发现的
  外部文件在完成时观察并记录；
- `complete-node` 必须提交本 Node 实际使用的非空 `input_files`；
- 完成时，已知路径绑定到Node启动时冻结的版本；首次发现的外部路径在完成时计算SHA-256；
- 即使文件在 Node 内被覆盖，最终血缘仍引用真正读取的旧版本；
- 旧版已经启动的 Node 可以从原 `step_inputs` 回退完成，避免会话无法恢复。

Plan 的 `depends_on` 保留为语义或执行依赖，不强制等同于文件依赖。直接依赖没有贡献实际
输入文件时只写入内部诊断提示，不阻止 Node 完成。

### 12.2 程序路径规范化

- 命令只来自成功的 `PostToolUse` Bash/PowerShell 事件；
- 程序候选来自本 Node 的真实代码产物和实际代码输入；
- 使用绝对路径、项目相对路径和唯一文件名与命令匹配；
- 内部保存规范化绝对路径，对外 JSON 导出项目相对路径；
- 代码完成门禁使用规范化后的实际程序集合，不再直接依赖命令字符串中的相对路径拼接。

### 12.3 动态 Plan

- 未来pending Node可以在其他Node开始前、执行期间和完成后修订；
- 实际Node始终绑定启动时的Plan Revision；
- active/completed Node不能从后续Revision删除，也不能改写定义；
- 后续 Revision 必须填写真实 `change_reason`；
- Plan 没有实质变化时拒绝创建空 Revision；
- Plugin 明确要求每个 Node 完成后判断剩余 Plan 是否仍然适用，但没有变化时不修订。

## 13. 2026-07-31 checkpoint 与 Run 输出归档

### 13.1 人工 checkpoint

`agentvast run` 新增 Run 级参数：

```text
--checkpoint plan    # 默认：每个Plan Revision确认后自动执行
--checkpoint node    # 每个Plan Revision确认后，每个Node完成后暂停
--checkpoint none    # 不暂停，保持全自动
```

Agent 使用无 payload 的记录命令打开 checkpoint：

```bash

```

打开 checkpoint 后，Claude 可以结束当前回复，但 Run 保持 `active`。用户下一条消息自动关联
刚完成的 Node、当前 Plan Revision 和 checkpoint 类型。明确的“继续”或“确认完成”分类为

`human_interventions`。指导、规划建议和异议继续按真实 workflow effect 记录，并可触发未来
Node 的 Plan Revision。

`plan`模式确认每个新Plan Revision，确认后自动执行到下一个Revision或当前Plan结束，且不

## 14. 2026-07-31 上下文压缩与中断恢复

真实 VAST Run `run_017e45fb2192` 在 `node-002` active 期间触发模型 context-window
上限，且此时手工 `/compact` 也被网关拒绝。原因是本地 Opus 4.8 的默认自动压缩可能直到
模型窗口极限才触发，而兼容网关可能采用更小或不同的有效窗口。

启动器现在为新 Run 和 resume 统一设置：

```text
CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000
CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=70
```

这使 Claude Code 按 200,000 token 计算窗口，在约 140,000 token 时尝试自动压缩。该配置
适用于有效上下文接近 200,000 token 的模型或网关；如果兼容网关限制更小，仍需降低计算
窗口或触发百分比。`run` 和 `resume` 支持用 `--compact-window` 与
`--compact-percent` 对单次启动覆盖默认值。插件新增：

- `PreCompact`：记录自动或手工压缩开始；
- `PostCompact`：记录压缩完成；
- `StopFailure`：记录上下文、网关或其他 API 失败；
- 压缩后的 `SessionStart`：重新注入当前 Run、Plan、active Node 和门禁规则。

所有 AgentVAST 启动和恢复命令同时加入
`--dangerously-skip-permissions`。它只关闭 Claude Code 的权限询问，不关闭 AgentVAST
PreToolUse 门禁。

### 14.1 两种恢复方式

普通终端关闭、网络中断且旧 transcript 仍可用：

```powershell
agentvast resume <run_id> --project "<project>"
```

上下文已经耗尽或旧 transcript 无法压缩：

```powershell
agentvast resume <run_id> --project "<project>" --fresh-session
```

fresh-session 创建新的 Claude session ID，并将其绑定到原 active Run。恢复提示只注入必要
状态：

- 原始任务和当前 Plan；
- completed Node 的结果与结论摘要；
- 当前 active Node；
- pending 用户输入；
- `result/<run_id>` 已有产物列表。

恢复不会修改 completed Node。存在 active Node 时，新 Claude 必须检查已有产物并继续同一
语义目标。真正启动 fresh-session 后，旧、新 session ID 和恢复原因写入内部
`ClaudeSessionRotated` Hook 事件。`--no-launch` 只预览命令，不改变 Run 的 session ID。

## 15. 2026-08-03 Plan、报告与Checkpoint调整

当前规则调整为：

- `required_artifacts`仍由每个Plan Node声明，但具体类别由Claude判断；
- 不再强制每个Node生成report，也不再强制整个Plan覆盖四类产物；
- report目录只接受有效JSON object，扩展名为 `.json`；
- `finish-run`只验证已经记录的产物未被删除或篡改，不检查四类是否齐全；
- Plan Revision只能删除或修改未来pending Node，active/completed Node定义不可变；
- 新Run的checkpoint模式为 `plan|node|none`，默认 `plan`；
- `plan`模式在每个新Plan Revision提交后自动等待人工确认，确认最新版本后自动执行到
  下一个Revision或当前Plan结束，任务结束时不再确认；
- `node`模式先确认每个Plan Revision，再在每个Node完成后暂停；
- 数据库保留旧 `final` Run的内部兼容逻辑，但CLI不再允许新建 `final` 模式Run。

本轮没有新增或运行自动测试，等待用户执行新的真实Claude Code Run手动验收。
