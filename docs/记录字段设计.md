# AgentVAST 记录字段设计

## 1. 目的

AgentVAST 对外记录 Coding Agent 真实完成的数据分析任务链。记录颗粒度统一称为
**Node**，不记录思维过程，也不把底层工具日志直接当作工作流。

AgentVAST 只记录和校验；数据读取、程序编写、方法选择、结果解释和分析决策由 Agent 完成。

## 2. Node 的统一含义

系统只使用一个业务概念：

```text
Node = 一个可独立说明、执行和验收的语义分析任务
```

Plan Revision 中的 `nodes` 是当时计划的 Node 定义；顶层 `nodes` 是这些 Node 的实际执行记录。
二者通过同一个 `node_id` 和 `plan_version` 对应。

```text
plan_revisions[].nodes[].node_id
                 ↓
nodes[].plan_version + nodes[].node_id
```

一个 Python 脚本、命令、重试、保存文件或临时产物本身不是 Node。保存输出应属于产生该输出
的语义 Node。

旧 SQLite 中可能仍有 `steps`、`step_id` 等内部列，用于兼容已有数据库和关联 Hook 事件；
这些不是对外业务字段。

## 3. 顶层结构

```json
{
  "schema_version": "1.3",
  "run": {},
  "plan_revisions": [],
  "nodes": [],
  "human_interventions": [],
  "file_lineage": []
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | string | 对外结构版本 |
| `run` | object | 整个任务的基本信息 |
| `plan_revisions` | array | 初始计划和后续计划修订 |
| `nodes` | array | 实际执行的语义任务链 |
| `human_interventions` | array | 实际改变工作流的人工介入 |
| `file_lineage` | array | 从 Node 输入输出派生的文件级血缘 |

## 4. Run

```json
{
  "run_id": "run_001",
  "task": "分析示例数据，说明主要特征和异常",
  "project_root": "C:/project",
  "result_root": "result/run_001",
  "agent": "claude-code",
  "session_id": "session-001",
  "status": "completed",
  "analysis_outcome": "answered",
  "started_at": "2026-07-28T10:00:00Z",
  "completed_at": "2026-07-28T10:15:00Z",
  "declared_inputs": [
    {
      "path": "result/sample.json",
      "sha256": "601b252d..."
    }
  ]
}
```

`status`：

```text
active
completed
aborted
failed
```

文件引用统一使用：

```json
{
  "path": "result/sample.json",
  "sha256": "601b252d..."
}
```

项目内文件使用相对路径，项目外文件使用规范化绝对路径。对外不记录文件大小。

## 5. Plan Revision

```json
{
  "version": 1,
  "created_at": "2026-07-28T10:00:05Z",
  "trigger": "initial",
  "change_reason": null,
  "nodes": [
    {
      "node_id": "node-001",
      "objective": "建立数据结构与质量概况",
      "depends_on": [],
      "required_artifacts": ["code", "data", "report"]
    },
    {
      "node_id": "node-002",
      "objective": "解释主要特征和异常",
      "depends_on": ["node-001"],
      "required_artifacts": ["code", "report", "visualization"]
    }
  ]
}
```

Plan Revision 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `version` | integer | 从 1 开始递增 |
| `created_at` | string | 创建时间 |
| `trigger` | string | 修订触发类型 |
| `change_reason` | string/null | 修订原因；初始计划为 `null` |
| `nodes` | array | 当前版本的完整 Node 计划 |

`trigger`：

```text
initial
agent_replan
human_intervention
```

计划 Node 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `node_id` | string | Run 内稳定的 Node 标识 |
| `objective` | string | 可独立解释和验收的分析目标 |
| `depends_on` | array[string] | 依赖的其他 Node |
| `required_artifacts` | array[string] | Node 完成前必须产生的产物类别 |

计划必须满足：

- 至少包含一个 Node；
- `node_id` 由 AgentVAST 按 `node-001`、`node-002` 顺序分配，Run 内永久稳定；
- `objective`统一使用中文；计划生成时终端与Web右上展示相同的Node编号、目标、依赖和产物类型，正式数据仍以SQLite结构化Plan为准；
- 依赖存在且无循环；
- 每个Node由Claude根据分析目标选择非空的 `required_artifacts` 子集；
- 不要求每个Node包含 `report`，也不要求Plan覆盖全部四类产物；
- Revision只能删除或修改未来pending Node；active/completed Node必须保留且定义不可变；
- 目标、依赖或产物要求变化时必须先创建新 Revision；
- 保存、导出、运行脚本等实现动作不能单独成为 Node。

用户未明确指定输入文件时，Claude可以在无active Node的受限只读发现阶段理解任务。
`declare-inputs`只是可选的提前登记方式，不构成输入白名单。Node启动后，Claude可以正常
使用其有权限访问的相关文件，并在Node完成时提交真实使用路径；AgentVAST对执行中首次发现
的外部文件观察SHA-256并补入Run输入。当前Plan全部完成不代表Run结束；后续轮次
继续在同一Run追加Plan Revision和Node。`New Task Trace`才会封存当前Run并创建新Run。

## 6. 实际执行 Node

```json
{
  "node_id": "node-001",
  "sequence": 1,
  "plan_version": 1,
  "objective": "建立数据结构与质量概况",
  "inputs": [
    {
      "path": "data/sample.json",
      "sha256": "601b252d..."
    }
  ],
  "operation": {
    "summary": "读取数据并检查结构、缺失情况和主要分布。",
    "commands": ["python result/run_001/code/node-001_profile.py"],
    "programs": ["result/run_001/code/node-001_profile.py"]
  },
  "outputs": [
    {
      "path": "result/run_001/data/node-001_profile.json",
      "sha256": "8a7c..."
    }
  ],
  "result_summary": "完成数据概况，发现两个高缺失率字段。",
  "analysis_conclusion": "建模前需要验证这两个字段是否可用。",
  "analysis_outcome": "partial",
  "recording_warnings": [],
  "status": "completed",
  "started_at": "2026-07-28T10:00:10Z",
  "completed_at": "2026-07-28T10:04:30Z"
}
```

字段：

| 字段 | 类型 | 产生方 | 说明 |
|---|---|---|---|
| `node_id` | string | Agent/AgentVAST | 与计划 Node 使用同一标识 |
| `sequence` | integer | AgentVAST | 实际执行顺序 |
| `plan_version` | integer | AgentVAST | 启动时的 Plan 版本 |
| `objective` | string | Plan | Node 的分析目标 |
| `inputs` | array | Agent + AgentVAST | 实际使用的数据文件版本 |
| `operation` | object | Agent + AgentVAST | 实际操作 |
| `outputs` | array | Agent + AgentVAST | 正式输出文件版本 |
| `result_summary` | string | Agent | 直接得到的事实结果 |
| `analysis_conclusion` | string/null | Agent | 结果说明了什么 |
| `analysis_outcome` | string | Agent | 本 Node 对分析目标的完成结果 |
| `recording_warnings` | array[string] | AgentVAST | 记录完整性提示，不等同于分析失败 |
| `status` | string | AgentVAST | 执行状态 |
| `started_at` | string | AgentVAST | 开始时间 |
| `completed_at` | string/null | AgentVAST | 完成或中断时间 |

Node 状态：

```text
active
completed
interrupted
failed
```

### 6.1 Node 边界

通常形成独立 Node：

- 有独立分析目标；
- 完成后有可说明的结果；
- 结果会影响后续分析；
- 输出会被另一个 Node 使用；
- 需要观察当前结果后才能决定下一项分析。

不单独形成 Node：

- 读取或保存文件；
- 运行命令或脚本；
- 编写函数；
- 重试失败操作；
- 创建缓存或调试文件；
- 确认已经存在的文件。

### 6.2 Operation

```json
{
  "summary": "检查数据结构和异常分布。",
  "commands": [],
  "programs": []
}
```

- `summary` 由 Agent 用一句话描述实际操作。
- `commands` 从真实 Bash/PowerShell 事件提取。
- `programs` 由成功命令与本 Node 的真实代码产物、代码输入进行路径匹配后生成。
- 使用 Read、Write 等内置工具而没有运行命令时，两个数组可以为空。
- 不要求 Agent额外提交算法、参数或操作类型。

### 6.3 输入与输出

完成 Node 时申报的实际输入可以是：

- Run 初始提供或Node执行中首次发现的外部输入；
- 已完成 Node 的输出。

`start-node` 不提交最终输入，只冻结当时已知的初始输入和上游输出版本。Agent 在
`complete-node` 时提交本 Node 真实使用过的文件路径：已知文件绑定到Node开始时冻结的
版本，执行中首次发现的外部文件在完成时登记。这样既不限制正常文件访问，也尽可能让
可变文件的血缘指向实际执行边界处的版本。

Plan 的 `depends_on` 表示语义或执行依赖，不必然产生文件传递。某个直接依赖没有贡献实际
输入文件时，AgentVAST 可以给出诊断提示，但不应据此否定真实的语义依赖。

输出由 AgentVAST 根据 Node 启动时的目录快照自动发现，而不是依赖 Agent 逐个申报。
正式产物统一保存在：

```text
result/<run_id>/code/
result/<run_id>/data/
result/<run_id>/report/
result/<run_id>/visualization/
```

每个新建文件的名称必须以生成它的 Node 编号加下划线开头，例如：

```text
node-001_profile.py
node-001_profile.json
node-001_findings.json
node-002_anomaly_chart.html
```

缓存、调试文件和 AgentVAST 自身文件不进入上述目录。Agent 可以在 `complete-node` 中省略
`output_files`；若提交该字段，它只用于与自动发现结果交叉核对。

active/completed Node 的“不可改写”只约束 Plan 定义，不冻结其产物文件。后续 Node 可以
读取、复用或原位编辑先前 Node 的文件。原位编辑时必须在 `input_files` 中声明该路径，
AgentVAST 将 Node 启动时冻结的旧版本作为输入，将编辑后的新版本作为当前 Node 输出；
文件名保留原来的 Node 前缀即可。未声明旧版本的原位修改会被拒绝。

同一 `path + sha256` 不能同时作为某个 Node 的输入和输出，因为这代表文件没有发生变化。

### 6.4 产物记录与提示

- `code`：识别本 Node 新增或修改的 `.py` 或 `.ipynb`，并尽可能和真实命令匹配；
- `data`：至少一个 `.csv`、`.json`、`.jsonl`、`.parquet`、`.feather` 或 `.arrow`；
- `report`：至少一个有效的 `.json` object，记录本Node需要保存的结构化报告；
- `visualization`：至少一个 `.html`、`.svg`、`.png`、`.jpg`、`.jpeg` 或 `.pdf`；
- 文件应当非空，新建文件应使用当前 Node 文件名前缀；
- `required_artifacts` 是 Plan 中的产物预期。实际缺失、空文件、命名偏差或无产物时，
  AgentVAST 仍忠实完成 Node 记录，并将问题写入 `recording_warnings`，不以记录系统替代
  Claude 对分析是否成立的判断。

### 6.5 结果与结论

```text
result_summary：实际得到了什么
analysis_conclusion：这些结果说明了什么
```

纯转换 Node 可以使用 `analysis_conclusion: null`，不能编造结论。

`analysis_outcome` 的枚举值为：

```text
answered
partial
insufficient_data
blocked
failed
not_assessed
```

Run 级 `analysis_outcome` 由各 Node 结果归纳，用于区分“执行完成”和“问题已得到回答”。

## 7. 人工介入

```json
{
  "intervention_id": "input_001",
  "original_text": "先验证异常，不要直接删除。",
  "type": "challenge",
  "active_node_id": "analyze_anomalies",
  "plan_version": 1,
  "workflow_effect": "增加异常来源复核，并暂缓删除。",
  "created_at": "2026-07-28T10:06:00Z",
  "applied_at": "2026-07-28T10:06:20Z"
}
```

类型：

```text
analysis_guidance
planning_input
challenge
```

普通交流 `conversation_only` 不进入最终 JSON。人工输入本身不是 Node；只有它实际触发的
验证、纠正或新分析目标才可能成为 Node。

人工checkpoint的明确确认或“继续”在内部记录为 `checkpoint_continue`。默认 `plan`
checkpoint关联每一个新建Plan Revision，并且确认版本必须等于当前最新版本；`node`模式
还会把后续Node checkpoint关联completed Node。确认事件
只用于解除运行门禁，不进入最终JSON。若用户提出异议、分析指导或下一步规划，则仍按上面的
三种正式人工介入类型记录。

## 8. 文件血缘

```json
{
  "node_id": "node-001",
  "inputs": [
    {"path": "result/sample.json", "sha256": "601b252d..."}
  ],
  "outputs": [
    {"path": "result/run_001/data/node-001_profile.json", "sha256": "8a7c..."}
  ]
}
```

`file_lineage` 从 `nodes[].inputs` 和 `nodes[].outputs` 自动生成，不由 Agent 单独提交。
没有输出的 Node 不生成文件血缘项。

## 9. Agent 最小提交内容

Agent 只提交：

```text
Plan：临时node_id别名、objective、depends_on、required_artifacts、必要时的change_reason
启动Node：node_id
完成Node：node_id、input_files、operation_summary、可选output_files、result_summary、analysis_conclusion、analysis_outcome
人工介入：type、workflow_effect
```

AgentVAST 自动提供：

```text
稳定Node编号、时间、状态、执行顺序、Plan版本、session关联
Node启动时的可用输入版本快照
产物自动发现、文件SHA-256、真实命令、规范化程序路径、文件血缘、记录提示
人工介入发生时的Node和Plan上下文
```

## 10. 不进入最终 JSON

- SQLite 内部 `steps/step_id` 等兼容键；
- 文件大小；
- 完成条件和门禁状态；
- 原始 Hook payload；
- Thought 或 chain-of-thought；
- 算法、参数和操作类型结构；
- 输出角色；
- 结构化 `processing_result`；
- 普通聊天；
- checkpoint 的纯确认/继续事件及内部等待状态；
- DAG 布局坐标。

## 11. 内部执行约束

每个实际 Node 必须对应其启动时 Plan Revision 中的一个 Node；实际任务依赖发生变化时，
必须先修订 Plan。对外 JSON 因而不增加 `depends_on_steps`，DAG 生成器直接使用相应
Plan Revision 的 `depends_on` 自动计算实际 Node 边。

Plan Revision只能调整未来pending Node。active/completed Node必须继续保留，且其
`objective`、`depends_on`、`required_artifacts`不能被后续Revision改写。

内部 SQLite 可以保留门禁状态、目录快照、原始 Hook 事件、完成条件和旧
`steps/step_id` 关联字段，以及 Run 的 `checkpoint_mode`、`awaiting_user`、
`checkpoint_kind`、Plan确认版本和checkpoint目标Step；这些不是对外JSON字段。

对外 JSON 默认保存为 `result/<run_id>/workflow.json`，与该 Run 的 `code/`、`data/`、
`report/` 和 `visualization/` 目录统一归档。内部 SQLite 仍保存于项目
`.agentvast/workflow.sqlite3`。

## 12. DAG 派生

DAG 根据以下事实自动生成：

```text
nodes[].plan_version
nodes[].node_id
plan_revisions[].nodes[].depends_on
nodes[].inputs
nodes[].outputs
human_interventions[].active_node_id
```

Agent 不提交 DAG Node、Edge 或前端布局。规范化 workflow JSON 是唯一事实来源。
