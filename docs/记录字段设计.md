# OpenTrace 记录字段设计

## 1. 文档目的

本文档定义 OpenTrace 对外导出的语义工作流 JSON。该 JSON 用于描述 Coding Agent
真实完成的数据分析任务链，而不是记录 Agent 的思维过程，也不是完整复制底层工具操作日志。

设计优先满足两个目标：

1. 以语义 Step 为颗粒度，完整记录 Agent 实际完成的数据分析 workflow。
2. 约束 Agent 以可记录、可解释且颗粒度合理的方式完成数据分析。

OpenTrace 只负责记录和校验。数据读取、程序编写、算法选择、结果解释以及下一步分析决策，
全部由 Agent 完成。

## 2. 设计原则

### 2.1 最小化 Agent 的额外工作

Agent 只提交无法从运行环境自动获得的语义信息：

- Step 的目标；
- 实际操作的自然语言摘要；
- 处理结果摘要；
- 分析结论；
- 人工介入对 workflow 造成的实际影响。

OpenTrace 自动记录或计算：

- Run、Step 和 session 标识；
- 时间和状态；
- 文件路径和 SHA-256；
- 实际执行的命令和程序路径；
- Plan 版本；
- Step 顺序；
- 文件级血缘。

不要求 Agent 为记录目的额外计算统计指标、分类算法、整理参数或判断输出文件角色。

### 2.2 语义记录与诊断日志分离

最终 workflow JSON 只包含可以解释真实分析过程的语义记录。

完整 Hook payload、权限检查、失败重试和底层工具事件可以保留在 SQLite 中用于诊断，
但不进入最终 workflow JSON。

### 2.3 不记录思维过程

OpenTrace 不保存或要求 Agent 提交 Thought、chain-of-thought、隐藏推理或未执行的分析设想。

### 2.4 文件级血缘

当前版本只记录文件级血缘：

```text
某个 Step 使用了哪些文件
→ 进行了什么操作
→ 产生了哪些文件
```

当前版本不记录字段级、行级或 item 级血缘。

### 2.5 对外记录与内部控制状态分离

规范化 workflow JSON 是面向查看、交换和前端展示的对外记录，不承担运行时门禁职责。

内部 SQLite 可以继续保存：

- Run 状态机；
- 当前 active Step；
- Step 完成条件；
- 原始 Hook 事件；
- 工具门禁结果；
- 未处理人工输入；
- 记录命令执行状态；
- 一致性校验信息。

这些字段用于保证 Claude 按照协议执行以及诊断失败原因，不属于对外 workflow JSON，
也不应要求 Agent 为其提供额外信息。

## 3. 顶层结构

最终导出 JSON 包含以下顶层字段：

```json
{
  "schema_version": "1.0",
  "run": {},
  "plan_revisions": [],
  "steps": [],
  "human_interventions": [],
  "file_lineage": []
}
```

| 字段 | 类型 | 必填 | 产生方 | 说明 |
|---|---|---:|---|---|
| `schema_version` | string | 是 | OpenTrace | 对外 JSON 结构版本 |
| `run` | object | 是 | OpenTrace | 整个分析任务的基本信息 |
| `plan_revisions` | array | 是 | Agent + OpenTrace | 初始计划及后续计划修改 |
| `steps` | array | 是 | Agent + OpenTrace | 实际发生的语义任务链 |
| `human_interventions` | array | 是 | 用户 + Agent + OpenTrace | 实际影响 workflow 的人工介入 |
| `file_lineage` | array | 是 | OpenTrace | 从 Step 输入输出自动生成的文件级血缘 |

空集合使用空数组 `[]`，不省略顶层字段。

## 4. `run`

`run` 记录整个数据分析任务的基本信息，不描述某个具体 Step。

### 4.1 示例

```json
{
  "run_id": "run_d416949472f1",
  "task": "分析示例数据，说明主要特征和异常",
  "project_root": "C:/Users/user/project",
  "agent": "claude-code",
  "session_id": "8ae50a34-1b1c-4d14-afcf-322268d93b33",
  "status": "completed",
  "started_at": "2026-07-28T10:00:00+08:00",
  "completed_at": "2026-07-28T10:15:00+08:00",
  "declared_inputs": [
    {
      "path": "result/sample_data_analysis.json",
      "sha256": "601b252d3708f411c5cb5b717d2a8e60659c340f111e963994e84a596c238675"
    }
  ]
}
```

### 4.2 字段

| 字段 | 类型 | 必填 | 产生方 | 说明 |
|---|---|---:|---|---|
| `run_id` | string | 是 | OpenTrace | Run 的唯一标识 |
| `task` | string | 是 | 启动参数 | 用户交给 Agent 的原始任务 |
| `project_root` | string | 是 | OpenTrace | 本次分析的项目根目录 |
| `agent` | string | 是 | OpenTrace | 执行平台，例如 `claude-code` |
| `session_id` | string | 是 | OpenTrace | Agent 平台的会话标识 |
| `status` | string | 是 | OpenTrace | Run 当前状态 |
| `started_at` | string | 是 | OpenTrace | ISO 8601 开始时间 |
| `completed_at` | string/null | 是 | OpenTrace | 完成或终止时间；运行中为 `null` |
| `declared_inputs` | array | 是 | 启动参数 + OpenTrace | 启动 Run 时声明的初始输入文件 |

`status` 允许值：

```text
active
completed
aborted
failed
```

### 4.3 文件引用

`declared_inputs`、Step 输入、Step 输出和文件血缘统一使用以下文件引用：

```json
{
  "path": "result/sample_data_analysis.json",
  "sha256": "601b252d..."
}
```

| 字段 | 类型 | 必填 | 产生方 | 说明 |
|---|---|---:|---|---|
| `path` | string | 是 | 启动参数、Agent 或 Hook | 文件路径 |
| `sha256` | string | 是 | OpenTrace | OpenTrace 自动计算的文件版本摘要 |

项目内文件优先保存相对于 `project_root` 的路径。项目外文件使用规范化绝对路径。

不记录文件 `size`。SHA-256 仅用于区分文件版本，不要求 Agent 计算。

## 5. `plan_revisions`

`plan_revisions` 记录 Agent 曾经声明的语义计划，以及计划在分析过程中如何变化。

Plan 表示“准备做什么”。实际完成了什么，以 `steps` 为准。

### 5.1 示例

```json
{
  "version": 1,
  "created_at": "2026-07-28T10:00:05+08:00",
  "trigger": "initial",
  "change_reason": null,
  "nodes": [
    {
      "node_id": "inspect_data",
      "objective": "检查数据结构和主要内容",
      "depends_on": []
    },
    {
      "node_id": "analyze_anomalies",
      "objective": "识别数据中的主要异常",
      "depends_on": [
        "inspect_data"
      ]
    }
  ]
}
```

### 5.2 Plan Revision 字段

| 字段 | 类型 | 必填 | 产生方 | 说明 |
|---|---|---:|---|---|
| `version` | integer | 是 | OpenTrace | 从 1 开始递增的 Plan 版本 |
| `created_at` | string | 是 | OpenTrace | Plan 版本创建时间 |
| `trigger` | string | 是 | OpenTrace | 创建该版本的触发原因 |
| `change_reason` | string/null | 是 | Agent | 修改计划的简短原因；初始计划为 `null` |
| `nodes` | array | 是 | Agent | 当前版本的语义节点 |

`trigger` 允许值：

```text
initial
agent_replan
human_intervention
```

`change_reason` 不是分析报告。只有 Plan 发生修改时才需要用一句话说明真实原因。

### 5.3 Plan Node 字段

| 字段 | 类型 | 必填 | 产生方 | 说明 |
|---|---|---:|---|---|
| `node_id` | string | 是 | Agent/OpenTrace | 当前 Plan 内唯一的节点标识 |
| `objective` | string | 是 | Agent | 一个可独立解释和验收的分析目标 |
| `depends_on` | array[string] | 是 | Agent | 该节点依赖的其他 `node_id` |

Plan Node 不记录：

- `step_type`；
- 算法；
- 参数；
- 命令；
- 程序；
- 文件；
- 执行状态。

节点状态可以根据实际 Step 自动推导，不作为 Plan 的原始字段保存。

### 5.4 Plan Revision 与实际 Step 的内部约束

OpenTrace 必须执行以下内部约束：

> 每个实际 Step 必须对应当前 Plan Revision 中的一个 Node；实际任务依赖发生变化时，
> 必须先修订 Plan。

具体规则：

1. `start-step` 的 `node_id` 必须存在于当前 Plan Revision。
2. Step 保存其启动时的 `plan_version` 和 `node_id`。
3. Plan Node 的依赖关系通过 `nodes[].depends_on` 表达。
4. 如果实际分析目标或依赖发生变化，Agent 必须先创建新的 Plan Revision，再启动对应 Step。
5. 已完成 Step 不允许被回写或重构；新的理解通过 Plan Revision 和后续 Step 表达。
6. 新 Plan Revision 应保留对已经完成工作的语义引用，不能通过重写计划隐藏真实历史。

在满足以上约束时，对外 JSON 不需要增加 `depends_on_steps`。DAG 生成器可以根据：

```text
Step.plan_version
+ Step.node_id
+ PlanRevision.nodes[].depends_on
+ steps[].inputs / steps[].outputs
```

自动计算实际 Step 之间的依赖关系。

如果文件输入输出已经形成依赖，则生成文件血缘边；如果只有语义依赖而没有文件传递，则根据
Plan Node 的 `depends_on` 生成 Step 依赖边。

Agent 不提交 DAG Node、DAG Edge 或 PROV Relation。DAG 是规范化 workflow JSON 的派生视图，
不是新的事实来源。

## 6. `steps`

`steps` 是最终 workflow JSON 的核心。每个 Step 表示一个真实发生、可独立说明和验收的
语义分析任务。

### 6.1 Step 边界

以下情况通常应当形成一个 Step：

- 有独立的数据分析目标；
- 有明确的完成条件；
- 完成后得到可以说明的结果；
- 结果会影响后续分析决策；
- 输出文件会被另一个语义任务使用。

以下情况本身不构成 Step：

- 运行一条命令；
- 读取一个文件；
- 编写一个 Python 函数；
- 创建一个临时文件；
- 因错误重试；
- 修改实现细节；
- 更换工具但分析目标没有变化。

一个 Python 脚本或中间文件只有在承载独立语义目标，或者其结果需要先被观察后才能决定
下一步时，才可能构成新的 Step。

### 6.2 示例

```json
{
  "step_id": "step_001",
  "sequence": 1,
  "plan_version": 1,
  "node_id": "inspect_data",
  "objective": "检查数据结构和主要内容",
  "inputs": [
    {
      "path": "result/sample_data_analysis.json",
      "sha256": "601b252d..."
    }
  ],
  "operation": {
    "summary": "读取 JSON 文件，检查顶层结构和主要记录类型。",
    "commands": [
      "python scripts/inspect_data.py"
    ],
    "programs": [
      "scripts/inspect_data.py"
    ]
  },
  "outputs": [
    {
      "path": "result/inspection_summary.json",
      "sha256": "8a7c..."
    }
  ],
  "result_summary": "完成数据结构检查，识别出员工事件、论坛帖子和内容分析三个主要部分。",
  "analysis_conclusion": "部分员工记录具有高度重复的统计结果，后续需要验证数据生成过程。",
  "status": "completed",
  "started_at": "2026-07-28T10:00:10+08:00",
  "completed_at": "2026-07-28T10:04:30+08:00"
}
```

### 6.3 Step 字段

| 字段 | 类型 | 必填 | 产生方 | 说明 |
|---|---|---:|---|---|
| `step_id` | string | 是 | OpenTrace | Step 唯一标识 |
| `sequence` | integer | 是 | OpenTrace | Step 在当前 Run 中的实际执行顺序 |
| `plan_version` | integer | 是 | OpenTrace | Step 启动时对应的 Plan 版本 |
| `node_id` | string | 是 | Agent/OpenTrace | 对应的 Plan Node |
| `objective` | string | 是 | Agent | 该 Step 的真实目标 |
| `inputs` | array | 是 | Agent + OpenTrace | 该 Step 实际使用的输入文件版本 |
| `operation` | object | 是 | Agent + OpenTrace | 实际进行了什么操作 |
| `outputs` | array | 是 | Agent + OpenTrace | 该 Step 产生的正式输出文件版本 |
| `result_summary` | string | 是 | Agent | 该操作直接得到了什么 |
| `analysis_conclusion` | string/null | 是 | Agent | 结果说明了什么；纯处理 Step 可以为 `null` |
| `status` | string | 是 | OpenTrace | Step 当前状态 |
| `started_at` | string | 是 | OpenTrace | Step 开始时间 |
| `completed_at` | string/null | 是 | OpenTrace | Step 完成或中断时间 |

Step 的 `status` 允许值：

```text
active
completed
interrupted
failed
```

### 6.4 `operation`

```json
{
  "summary": "运行脚本检查数据结构和重复记录。",
  "commands": [
    "python scripts/inspect_data.py"
  ],
  "programs": [
    "scripts/inspect_data.py"
  ]
}
```

| 字段 | 类型 | 必填 | 产生方 | 说明 |
|---|---|---:|---|---|
| `summary` | string | 是 | Agent | 一句话说明对数据实际做了什么 |
| `commands` | array[string] | 是 | OpenTrace | 从真实工具调用中自动提取的分析命令 |
| `programs` | array[string] | 是 | OpenTrace | 从真实命令或文件操作中自动识别的程序路径 |

`commands` 不包含 OpenTrace 自身的记录命令。

不单独记录：

- `algorithms`；
- `parameters`；
- `operation_types`；
- 工具分类；
- Agent 未实际执行的程序。

如果某个算法或参数对理解该 Step 很重要，Agent 可以自然地写进 `summary`，不要求结构化。

### 6.5 `inputs`

`inputs` 记录该 Step 实际使用的文件，而不是 Agent 搜索过但没有用于该 Step 的所有文件。

输入路径优先由 Hook 捕获；无法自动确定语义归属时，由 Agent 在 Step 开始时声明。SHA-256
始终由 OpenTrace 计算。

一个 Step 至少应当有一个输入文件。没有文件输入的纯规划或交流活动不应创建 Step。

### 6.6 `outputs`

`outputs` 只记录 Step 产生的正式文件：

```json
[
  {
    "path": "result/inspection_summary.json",
    "sha256": "8a7c..."
  }
]
```

没有输出文件时使用空数组：

```json
[]
```

输出路径优先由 Hook 捕获；如果程序内部产生文件而 Hook 无法识别，则由 Agent 在 Step
完成时声明路径。Agent 不需要提供文件大小、SHA-256 或输出角色。

不进入 `outputs`：

- 缓存；
- 调试文件；
- 未被后续使用且没有独立价值的临时文件；
- OpenTrace 自身的数据库和导出文件。

### 6.7 `result_summary`

`result_summary` 用自然语言记录操作直接产生的事实性结果：

```json
"result_summary": "完成数据结构检查，发现多个员工记录具有相同事件统计。"
```

不要求 Agent 将结果重新整理成结构化指标对象。具体数字只有在本来就是重要分析结果时，
才自然写入该字段。

不再使用：

```json
{
  "processing_result": {
    "total_posts": 108,
    "posts_with_source": 3
  }
}
```

### 6.8 `analysis_conclusion`

`analysis_conclusion` 记录 Agent 对结果的解释：

```json
"analysis_conclusion": "高度重复的统计可能来自数据生成或聚合错误。"
```

两者的边界：

```text
result_summary：实际得到了什么
analysis_conclusion：这些结果说明了什么
```

数据清洗、格式转换或脚本准备等纯处理 Step 如果没有独立分析结论，使用 `null`，不要编造结论。

## 7. `human_interventions`

`human_interventions` 只记录实际改变分析过程的人工输入。普通交流可以保留在内部诊断日志中，
但不进入最终 workflow JSON。

### 7.1 示例

```json
{
  "intervention_id": "input_001",
  "original_text": "不要直接判断是数据泄漏，先验证文件内容。",
  "type": "challenge",
  "active_step_id": "step_002",
  "plan_version": 1,
  "workflow_effect": "增加文件内容验证步骤，并暂缓形成安全事件结论。",
  "created_at": "2026-07-28T10:06:00+08:00",
  "applied_at": "2026-07-28T10:06:20+08:00"
}
```

### 7.2 字段

| 字段 | 类型 | 必填 | 产生方 | 说明 |
|---|---|---:|---|---|
| `intervention_id` | string | 是 | OpenTrace | 人工介入唯一标识 |
| `original_text` | string | 是 | 用户 | 用户输入原文 |
| `type` | string | 是 | Agent | 人工介入类型 |
| `active_step_id` | string/null | 是 | OpenTrace | 介入发生时的 active Step |
| `plan_version` | integer/null | 是 | OpenTrace | 介入发生时的 Plan 版本 |
| `workflow_effect` | string | 是 | Agent | 该输入实际如何改变了分析 |
| `created_at` | string | 是 | OpenTrace | 输入时间 |
| `applied_at` | string | 是 | OpenTrace | 影响被落实的时间 |

`type` 允许值：

```text
analysis_guidance
planning_input
challenge
```

不记录 `structured_summary`，因为它与 `original_text` 和 `workflow_effect` 重复。

人工输入本身不是 Step。它可以：

- 改变当前 Step 的执行方法；
- 触发 Plan 修订；
- 触发后续验证或纠正 Step；
- 对之前的处理结果提出异议。

## 8. `file_lineage`

`file_lineage` 是从 `steps[].inputs` 和 `steps[].outputs` 自动生成的派生视图。

### 8.1 示例

```json
{
  "step_id": "step_001",
  "inputs": [
    {
      "path": "result/sample_data_analysis.json",
      "sha256": "601b252d..."
    }
  ],
  "outputs": [
    {
      "path": "result/inspection_summary.json",
      "sha256": "8a7c..."
    }
  ]
}
```

| 字段 | 类型 | 必填 | 产生方 | 说明 |
|---|---|---:|---|---|
| `step_id` | string | 是 | OpenTrace | 执行文件转换或生成的 Step |
| `inputs` | array | 是 | OpenTrace | 该 Step 的文件输入 |
| `outputs` | array | 是 | OpenTrace | 该 Step 的文件输出 |

`file_lineage` 不由 Agent 提交，也不是独立事实来源。唯一事实来源是：

```text
steps[].inputs
steps[].outputs
```

保留该字段是为了让前端无需重新计算即可展示文件级血缘。

没有输出文件的分析 Step 不生成文件血缘项。

## 9. Agent 与 OpenTrace 的责任边界

### 9.1 Agent 必须提供

每个 Step 只要求 Agent 提供以下语义信息：

```text
objective
operation.summary
result_summary
analysis_conclusion
```

Agent 还需要在 OpenTrace 无法自动识别时，声明实际输入和输出文件路径。

人工介入发生后，Agent 需要提供：

```text
type
workflow_effect
```

Plan 由 Agent 提供：

```text
nodes[].objective
nodes[].depends_on
change_reason（仅修改计划时）
```

### 9.2 OpenTrace 必须自动提供

```text
所有 ID
所有时间
所有状态
Plan 版本
Step 顺序
session 关联
文件 SHA-256
实际分析命令
实际程序路径
文件级血缘
人工介入发生时的 Step 和 Plan 上下文
```

## 10. 不进入最终 workflow JSON 的内容

以下信息可以保留在 SQLite 内部用于调试和一致性检查，但不进入对外 JSON：

- Run 状态机和当前门禁状态；
- Step 内部完成条件；
- Thought、chain-of-thought 或隐藏推理；
- 完整 Hook payload；
- 重复的 `payload_json`；
- `PreToolUseBlocked` 等门禁诊断事件；
- 权限请求与权限响应；
- OpenTrace 自身的记录命令；
- 没有改变语义结果的命令重试；
- Agent 原始响应全文；
- 数据库内部行 ID；
- 文件大小；
- 临时文件和缓存；
- 结构化 `algorithms`；
- 结构化 `parameters`；
- `operation_types`；
- 输出文件 `role`；
- 结构化 `processing_result`；
- 普通聊天和 `conversation_only` 输入。

这些内部信息可以用于判断 Run 是否有效，但不能作为前端展示的语义 workflow 字段。

## 12. 最终语义

最终 JSON 应当能够直接回答：

```text
这是一次什么任务？
Agent 原本计划做什么？
Agent 实际完成了哪些语义 Step？
每个 Step 使用了什么文件？
Agent 对数据进行了什么操作？
实际执行了哪些命令或程序？
产生了哪些文件？
得到了什么结果？
形成了什么分析结论？
人在什么时刻如何改变了 workflow？
文件经过哪些 Step 发生了变化？
```

如果一个字段不能帮助回答以上问题，并且只是为了调试或增加结构完整性，就不应进入最终
workflow JSON。
