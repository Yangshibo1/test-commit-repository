# OpenTrace 记录字段设计

## 1. 目的

OpenTrace 对外记录 Coding Agent 真实完成的数据分析任务链。记录颗粒度统一称为
**Node**，不记录思维过程，也不把底层工具日志直接当作工作流。

OpenTrace 只记录和校验；数据读取、程序编写、方法选择、结果解释和分析决策由 Agent 完成。

## 2. Node 的统一含义

系统只使用一个业务概念：

```text
Node = 一个可独立说明、执行和验收的语义分析任务
```

Plan Revision 中的 `nodes` 是当时计划的 Node 定义；顶层 `nodes` 是这些 Node 的实际执行记录。
二者通过同一个 `node_id` 和 `plan_version` 对应。

```text
plan_revisions[].nodes[].node_id
                 ↓
nodes[].plan_version + nodes[].node_id
```

一个 Python 脚本、命令、重试、保存文件或临时产物本身不是 Node。保存输出应属于产生该输出
的语义 Node。

旧 SQLite 中可能仍有 `steps`、`step_id` 等内部列，用于兼容已有数据库和关联 Hook 事件；
这些不是对外业务字段。

## 3. 顶层结构

```json
{
  "schema_version": "1.1",
  "run": {},
  "plan_revisions": [],
  "nodes": [],
  "human_interventions": [],
  "file_lineage": []
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | string | 对外结构版本 |
| `run` | object | 整个任务的基本信息 |
| `plan_revisions` | array | 初始计划和后续计划修订 |
| `nodes` | array | 实际执行的语义任务链 |
| `human_interventions` | array | 实际改变工作流的人工介入 |
| `file_lineage` | array | 从 Node 输入输出派生的文件级血缘 |

## 4. Run

```json
{
  "run_id": "run_001",
  "task": "分析示例数据，说明主要特征和异常",
  "project_root": "C:/project",
  "agent": "claude-code",
  "session_id": "session-001",
  "status": "completed",
  "started_at": "2026-07-28T10:00:00Z",
  "completed_at": "2026-07-28T10:15:00Z",
  "declared_inputs": [
    {
      "path": "result/sample.json",
      "sha256": "601b252d..."
    }
  ]
}
```

`status`：

```text
active
completed
aborted
failed
```

文件引用统一使用：

```json
{
  "path": "result/sample.json",
  "sha256": "601b252d..."
}
```

项目内文件使用相对路径，项目外文件使用规范化绝对路径。对外不记录文件大小。

## 5. Plan Revision

```json
{
  "version": 1,
  "created_at": "2026-07-28T10:00:05Z",
  "trigger": "initial",
  "change_reason": null,
  "nodes": [
    {
      "node_id": "profile_data",
      "objective": "建立数据结构与质量概况",
      "depends_on": []
    },
    {
      "node_id": "analyze_anomalies",
      "objective": "解释主要特征和异常",
      "depends_on": ["profile_data"]
    }
  ]
}
```

Plan Revision 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `version` | integer | 从 1 开始递增 |
| `created_at` | string | 创建时间 |
| `trigger` | string | 修订触发类型 |
| `change_reason` | string/null | 修订原因；初始计划为 `null` |
| `nodes` | array | 当前版本的完整 Node 计划 |

`trigger`：

```text
initial
agent_replan
human_intervention
```

计划 Node 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `node_id` | string | Run 内稳定的 Node 标识 |
| `objective` | string | 可独立解释和验收的分析目标 |
| `depends_on` | array[string] | 依赖的其他 Node |

计划必须满足：

- 至少包含一个 Node；
- `node_id` 唯一；
- 依赖存在且无循环；
- 已启动的 Node 不能被后续 Revision 删除或改写；
- 目标或依赖变化时必须先创建新 Revision；
- 保存、导出、运行脚本等实现动作不能单独成为 Node。

## 6. 实际执行 Node

```json
{
  "node_id": "profile_data",
  "sequence": 1,
  "plan_version": 1,
  "objective": "建立数据结构与质量概况",
  "inputs": [
    {
      "path": "result/sample.json",
      "sha256": "601b252d..."
    }
  ],
  "operation": {
    "summary": "读取数据并检查结构、缺失情况和主要分布。",
    "commands": ["python scripts/profile.py"],
    "programs": ["scripts/profile.py"]
  },
  "outputs": [
    {
      "path": "result/profile.json",
      "sha256": "8a7c..."
    }
  ],
  "result_summary": "完成数据概况，发现两个高缺失率字段。",
  "analysis_conclusion": "建模前需要验证这两个字段是否可用。",
  "status": "completed",
  "started_at": "2026-07-28T10:00:10Z",
  "completed_at": "2026-07-28T10:04:30Z"
}
```

字段：

| 字段 | 类型 | 产生方 | 说明 |
|---|---|---|---|
| `node_id` | string | Agent/OpenTrace | 与计划 Node 使用同一标识 |
| `sequence` | integer | OpenTrace | 实际执行顺序 |
| `plan_version` | integer | OpenTrace | 启动时的 Plan 版本 |
| `objective` | string | Plan | Node 的分析目标 |
| `inputs` | array | Agent + OpenTrace | 实际使用的数据文件版本 |
| `operation` | object | Agent + OpenTrace | 实际操作 |
| `outputs` | array | Agent + OpenTrace | 正式输出文件版本 |
| `result_summary` | string | Agent | 直接得到的事实结果 |
| `analysis_conclusion` | string/null | Agent | 结果说明了什么 |
| `status` | string | OpenTrace | 执行状态 |
| `started_at` | string | OpenTrace | 开始时间 |
| `completed_at` | string/null | OpenTrace | 完成或中断时间 |

Node 状态：

```text
active
completed
interrupted
failed
```

### 6.1 Node 边界

通常形成独立 Node：

- 有独立分析目标；
- 完成后有可说明的结果；
- 结果会影响后续分析；
- 输出会被另一个 Node 使用；
- 需要观察当前结果后才能决定下一项分析。

不单独形成 Node：

- 读取或保存文件；
- 运行命令或脚本；
- 编写函数；
- 重试失败操作；
- 创建缓存或调试文件；
- 确认已经存在的文件。

### 6.2 Operation

```json
{
  "summary": "检查数据结构和异常分布。",
  "commands": [],
  "programs": []
}
```

- `summary` 由 Agent 用一句话描述实际操作。
- `commands` 从真实 Bash/PowerShell 事件提取。
- `programs` 从真实命令或文件操作识别。
- 使用 Read、Write 等内置工具而没有运行命令时，两个数组可以为空。
- 不要求 Agent额外提交算法、参数或操作类型。

### 6.3 输入与输出

输入只能是：

- Run 声明的初始输入；
- 已完成 Node 的输出。

输出只记录正式产物。缓存、调试文件和 OpenTrace 自身文件不进入输出。

同一 `path + sha256` 不能同时作为某个 Node 的输入和输出，因为这代表文件没有发生变化。

### 6.4 结果与结论

```text
result_summary：实际得到了什么
analysis_conclusion：这些结果说明了什么
```

纯转换 Node 可以使用 `analysis_conclusion: null`，不能编造结论。

## 7. 人工介入

```json
{
  "intervention_id": "input_001",
  "original_text": "先验证异常，不要直接删除。",
  "type": "challenge",
  "active_node_id": "analyze_anomalies",
  "plan_version": 1,
  "workflow_effect": "增加异常来源复核，并暂缓删除。",
  "created_at": "2026-07-28T10:06:00Z",
  "applied_at": "2026-07-28T10:06:20Z"
}
```

类型：

```text
analysis_guidance
planning_input
challenge
```

普通交流 `conversation_only` 不进入最终 JSON。人工输入本身不是 Node；只有它实际触发的
验证、纠正或新分析目标才可能成为 Node。

## 8. 文件血缘

```json
{
  "node_id": "profile_data",
  "inputs": [
    {"path": "result/sample.json", "sha256": "601b252d..."}
  ],
  "outputs": [
    {"path": "result/profile.json", "sha256": "8a7c..."}
  ]
}
```

`file_lineage` 从 `nodes[].inputs` 和 `nodes[].outputs` 自动生成，不由 Agent 单独提交。
没有输出的 Node 不生成文件血缘项。

## 9. Agent 最小提交内容

Agent 只提交：

```text
Plan：node_id、objective、depends_on、必要时的change_reason
启动Node：node_id、input_files
完成Node：node_id、operation_summary、output_files、result_summary、analysis_conclusion
人工介入：type、workflow_effect
```

OpenTrace 自动提供：

```text
时间、状态、执行顺序、Plan版本、session关联
文件SHA-256、真实命令、程序路径、文件血缘
人工介入发生时的Node和Plan上下文
```

## 10. 不进入最终 JSON

- SQLite 内部 `steps/step_id` 等兼容键；
- 文件大小；
- 完成条件和门禁状态；
- 原始 Hook payload；
- Thought 或 chain-of-thought；
- 算法、参数和操作类型结构；
- 输出角色；
- 结构化 `processing_result`；
- 普通聊天；
- DAG 布局坐标。

## 11. DAG 派生

DAG 根据以下事实自动生成：

```text
nodes[].plan_version
nodes[].node_id
plan_revisions[].nodes[].depends_on
nodes[].inputs
nodes[].outputs
human_interventions[].active_node_id
```

Agent 不提交 DAG Node、Edge 或前端布局。规范化 workflow JSON 是唯一事实来源。
